# 派工 prompt 模板

> 用法：複製對應模板，填 `【】` 空格，作為 Agent tool 的 prompt。model 選擇見 `dispatch.md` §3；
> 不確定用哪個 subagent_type / model 時，每個模板開頭有預設值。
> 每個模板已內建「三件套」（目標動機／驗收條件／回報格式）與回報合約，不要刪這些段落。

## 1. 搜尋定位（東西在哪）

subagent_type: `Explore`；model: `sonnet`（純找檔案位置可用 `haiku`）

```
在 repo 中定位：【要找什麼，例如「免費限次的判斷邏輯」】。
背景：【為什麼要找，例如「用戶要把每日免費次數由 3 改成 5」】。
搜尋廣度：【quick / medium / very thorough】。
可能相關的關鍵字：【例如 playlimit, freeLimit, daily】。

回報格式（嚴格遵守）：
- 每個相關位置一行：檔案:行號 ＋ 一句它是做什麼的。
- 最後一句：你認為改動的正確入口點是哪一個、為什麼。
- 不要貼超過 5 行的代碼原文。找不到就列出你搜過的關鍵字和目錄，說「未找到」。
```

## 2. 實作（寫代碼）

subagent_type: `general-purpose`；model: `sonnet`

```
任務：【改什麼，一句話】。
動機：【用戶想要什麼效果，為什麼】。
範圍：只准動這些檔案：【清單】。範圍外發現問題只記錄不修改。
專案背景：先讀 CLAUDE.md【kid-star 任務加：與 kid-star/CLAUDE.md】。

驗收條件（完成前逐條自查）：
1. 【功能條件，例如「每日免費次數上限變為 5，超過後顯示現有的鎖定畫面」】
2. 驗證命令通過：【py_compile / cd kid-star && npm run build / JSON.parse，照 CLAUDE.md 完工必做選】
3. diff 只含本任務改動。
【4. 行為驗證（如適用）：npm run preview + Playwright 開【頁面】確認無 console error】

完成後 commit 到分支【分支名】並 push（不開 PR、不碰 main）。

回報格式：改了哪些檔案（檔案:行號）、每條驗收條件 PASS/FAIL＋證據、
一句「還沒做／做不了」的事（沒有就寫「無」）。不要貼整段代碼。
```

## 3. 重構（不改行為的整理）

subagent_type: `general-purpose`；model: `sonnet`；改動跨 5 檔以上先派 `Plan` 出計劃

```
重構任務：【例如「把 4 個遊戲各自的出題去重邏輯收斂到 quizEngine」】。
動機：【例如「同樣邏輯抄了 4 份，改一處漏三處」】。
硬約束：對外行為不得改變——【寫清楚什麼算「行為」，例如「遊戲出題結果、儲存格式、URL 都不變」】。

驗收條件：
1. 驗證命令通過：【照 CLAUDE.md 完工必做】。
2. 重複邏輯出現次數：重構前【N】處 → 重構後 1 處（用 grep 證明，寫出 grep 命令與結果行數）。
3. diff 中沒有任何行為改動（新功能、修 bug 都不算重構，發現 bug 記錄不修）。

完成後 commit 到【分支名】並 push。
回報格式：動了哪些檔案（檔案:行號）、grep 前後對比、發現但沒修的問題清單。
```

## 4. 研究（查資料、比方案）

subagent_type: `general-purpose`（Claude Code/API 問題用 `claude-code-guide`）；model: `sonnet`，結論要做高風險決策時用 `opus`

```
研究問題：【一句話，例如「yfinance 對港股的 dividend 數據可靠嗎，有無替代」】。
動機／要支撐的決策：【例如「決定股息篩選功能用哪個數據源」】。
要求：
- 只信官方文件與一手來源，引用時附 URL。
- 區分「查證過的事實」與「你的推測」，推測要標明。
- 查不到的就寫查不到，不准編造。

回報格式：
- 結論先行（3 句內，直接回答研究問題）。
- 證據清單：每條一行＋來源 URL。
- 完整筆記落檔到【scratchpad 路徑或 .claude/notes/xxx.md】，回報只給路徑。
```

## 5. 審查／驗收（檢查別人或自己的工作）

subagent_type: `verifier`（驗收）或 `general-purpose`＋model `opus`（深度審查／第二意見）

```
驗收對象：【分支名或檔案清單】。
背景：【這項工作聲稱做了什麼】。
驗收條件（逐條找證據）：
1. 【條件＋怎麼驗，例如「math.json 新增 5 題且無重複題幹——grep 題幹關鍵字」】
2. 【驗證命令＋預期結果】
3. 【…】

規則：不要相信任何聲稱，一切以檔案內容與命令輸出為準。只驗收不修復。
回報格式：每條 PASS/FAIL＋證據（檔案:行號 或命令輸出關鍵行），最後一行 ACCEPT 或 REJECT。
```

## 多答案評審（高風險判斷用，dispatch §6）

1. 同一個問題派 2–3 個獨立 agent（互相看不到對方），用模板 2/4 各自作答。
2. 再開一個 `opus` 評審：
```
你是評審。以下是同一問題的【N】份獨立方案：【方案路徑清單】。
評分維度：正確性／簡單性／與現有代碼一致性（權重 3/2/1）。
回報：每份方案每維度 1-5 分＋一句理由，最後選出一份並說明主要勝出點。
不要自己寫第四份方案。
```
