# 判斷力外化：rubric 與 checklist

> 這些判準原本靠「模型夠強自然會判對」。寫在這裡，是讓任何等級的模型照著判也判對。
> 每條有正例（✅ 該這樣）和反例（❌ 不該這樣）。升降級的執行細節在 `dispatch.md` §7。

## 1. 何時該升級模型

**升級訊號（命中任何一條就升）：**
- 同一個錯誤修了兩次還在（不是兩個不同錯，是同一個）。
- 需要同時在腦中放 3 個以上檔案的互動才能推理（例如改 quizEngine 要同時顧 registry、progress、playlimit）。
- 任務涉及高風險面：部署行為、`kid-star/src/lib/playlimit.js` 產品規則、股票分析的計分/回測邏輯（用戶拿來做投資判斷）。
- 你發現自己在「猜」——寫出的修法自己說不出為什麼會有效。

✅ 正例：sonnet 修 build error，改了兩次同一個 import 錯誤還在爆 → 打包兩次失敗軌跡升 opus。
❌ 反例：改一個 typo 級的小錯第一次沒改對，就升 opus——先看清楚錯誤訊息再試第二次，兩輪內解決不了才升。

## 2. 何時算「真的完成」

**全部滿足才算完成（缺一條就不是完成，是「進行中」）：**
1. CLAUDE.md「完工必做」的驗證命令跑過且通過，輸出在對話裡可見。
2. `git diff` 只含本任務範圍內的改動（多出來的順手改動 = 沒完成，先移除或另開分支）。
3. 改動已 commit 並 push 到 `claude/*` 分支。
4. 跨 3 檔以上或高風險改動：verifier agent 回了 ACCEPT。
5. 對用戶的回報說清楚：改了什麼、怎麼驗證的、有什麼沒做。

✅ 正例：「加了 5 題數學題。JSON.parse 驗證通過、npm run build 通過、grep 確認題幹無重複、已 push，PR #17。」
❌ 反例：「已經加好題目了！」——沒跑驗證、沒提 push。這句話在本制度裡等於「我還沒做完」。

## 3. 何時該停下來問用戶

**先問再動（命中任何一條）：**
- 動作不可逆或對外可見：merge 進 main（=上線）、刪除資料/檔案、對外發送（email/Telegram）、改 GitHub 設定。
- 需求有兩種以上合理解讀，而且做錯方向的重工成本高（超過半小時的工作量）。
- 要改產品規則：免費限次、計分邏輯、收費相關、題目難度定位。
- opus 也解不掉的技術死路（帶失敗軌跡問，格式：目標／試了哪兩條路／各自卡在哪／建議下一步 2 選 1）。

**不要問（自己決定）：**
- 有慣例可循的（命名、代碼風格、commit 訊息格式——看現有代碼跟 git log）。
- 可逆且便宜的內部決策（先做 A 還是先做 B、臨時檔放哪）。

✅ 正例：用戶說「限時心算調快啲」沒給數值 → 問「而家 30 秒，改 20 定 15？」附現值。
❌ 反例：問「新變數叫 questionPool 定 questionBank？」——看鄰近代碼自己定。

## 4. 什麼訊號代表方向錯了（該換路，不是再試）

**命中任何一條，停下來，把現狀寫進 TaskUpdate，換方法或升級：**
- 同一招修第三次（dispatch §7 的兩輪上限就是為這個）。
- 每修好一處就爆出兩處新的——說明改錯了層，該往上游找根因。
- 你開始寫 workaround 而不是修因：加 try/catch 吞錯、寫死特例值、加 setTimeout 等時序、繞過驗證。
- diff 大小超出任務合理範圍 3 倍以上（改 5 題題目不該動到 quizEngine）。
- 需要「先改 A 才能改 B 才能改 C」鏈超過 3 層——先回頭確認任務是不是該這樣做。

✅ 正例：修遊戲不重複出題，發現要在 4 個遊戲各自 patch → 停，改成在 quizEngine 一處解決（歷史先例：943ff94 就是這樣做的）。
❌ 反例：測試頁面載入不到，就往 fetch 加 3 秒 retry——沒查是不是 BASE_PATH 寫死了絕對路徑（本專案已知坑，見 kid-star/CLAUDE.md）。

## 5. 品質底線怎麼驗

**分層驗，從便宜到貴，全過才算過：**
1. **語法層**：py_compile / node --check / JSON.parse（秒級，永遠要跑）。
2. **建置層**：`npm run build`（kid-star 任何改動）。
3. **行為層**：改了遊戲邏輯或頁面 → 實跑一次。本環境有 Chromium＋Playwright（executablePath: `/opt/pw-browsers/chromium`），可以 `npm run preview` 後開頁面截圖、看 console 有沒有 error。做不到實跑至少要在 build 產物 grep 確認改動有進去。
4. **驗收層**：跨 3 檔以上或高風險 → verifier agent（dispatch §6）。

✅ 正例：改了 TrafficLight.jsx 的節奏邏輯 → build 過後，preview 起服務，Playwright 開該遊戲頁，確認無 console error、截圖給用戶看。
❌ 反例：「build 過了所以遊戲邏輯是對的」——build 只驗語法和依賴，驗不了「黃燈會不會出現」。

## 6. 誠實條款：這套制度補不到的事

拆解＋驗證＋多答案評審，補得了**執行品質**；以下兩類補不了，遇到就照指示辦，不要假裝能：

- **品味判斷**（UI 好不好看、文案語氣自不自然、題目對小二學生難不難、投資參數合不合理）：機械驗證只能保證「沒壞」，保證不了「好」。做法：出 2–3 個候選讓用戶挑，或明說「這是品味判斷，我的建議是 X 但請你過目」。不准用「已優化」帶過。
- **模糊需求**（用戶一句話有多種合理展開）：不要挑一種悶頭做完。做法：小成本就做最保守解讀並在回報標明「我採取了解讀 A，如果你要的是 B 告訴我」；大成本就先問（§3）。

另外兩個已知極限，照實對待：
- **compact 失憶**：context 壓縮後你會失去細節。防禦：靠 TaskCreate 存目標、靠檔案存產出，不靠記性。
- **自驗盲區**：自己驗自己的工作永遠偏樂觀。防禦：dispatch §6，驗收給 fresh-context 的 verifier。
