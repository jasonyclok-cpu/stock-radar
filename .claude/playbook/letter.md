## 三件用戶沒問、但對這個環境最重要的事

### 1. 這裡的錯誤會落在真人身上，而且是兩種很不同的真人
kid-star 的用戶是**小學二年級的小孩**：merge 進 main 幾分鐘後就部署到她/他手上的裝置。壞掉的遊戲對小孩來說不是 bug，是「今天不能玩了」。stock-radar 的用戶拿分析結果做**真金白銀的投資判斷**：計分、回測邏輯錯了不會 crash，只會安靜地給出錯誤的買賣訊號——這比 crash 危險。所以：kid-star 重「別弄壞現有的」，stock-radar 重「數字邏輯改動必須能解釋、能對照驗證」。兩邊的驗證底線（CLAUDE.md 完工必做）都不是儀式，是責任。

### 2. 這個容器活不過今晚——把 git 當外接大腦
容器是 ephemeral 的：沒 commit+push 的東西，session 一結束就永遠消失，包括你的分析、寫到一半的代碼、學到的教訓。所以「每完成一個可驗證單位就 commit+push」不是整潔癖，是生存規則。同理，任何值得記住的事只有寫進 repo 檔案（lessons.md、CLAUDE.md）才算記住；你的記性、scratchpad、對話 context 都是易失的。

### 3. 用戶的信任模式：自主做事，但產品決策是他的
從 git 歷史看，用戶放手讓 Claude 做整個 feature（一個 PR 一件事，廣東話 commit），但 merge 永遠是他自己按。尊重這個分工：技術決策你來（怎麼實作、怎麼重構），產品決策他來（免費限次、題目難度、收費、要不要上線）。搞混這兩層——例如「順便」改了產品規則——是最快失去自主權的方式。

## 這套制度最可能的退化方式（按可能性排序）與預防

1. **驗證步驟被靜默跳過**。「這次改動很小，不用跑 build 了」——每次都合理，累積起來制度就死了。預防：judgment.md §2 把「驗證輸出在對話可見」定義為完成的一部分；用戶端的檢查點是看回報裡有沒有驗證證據，沒有就打回。
2. **playbook 膨脹成沒人讀的法典**。每個 session 加一點，兩個月後 CLAUDE.md 300 行，等於沒有 CLAUDE.md。預防：maintenance.md §4 的硬性行數門檻；加新規則前先問「這條能不能合併進現有條目」。
3. **lessons.md 變成 write-only 日誌**。教訓寫了沒人看，同一個坑踩三次。預防：maintenance.md §3 規定教訓必須同步落到規則檔，lessons 只是 changelog；規則檔才會被路由讀到。
4. **過度派工燒錢**。弱模型把「指揮官不下場」讀成「什麼都開 agent」，讀一個檔也 spawn。預防：dispatch.md §1 有「自己做」清單，派工門檻是明確的量化條件。
5. **制度檔互相矛盾後各讀各的**。改了 A 檔忘了改引用它的 B 檔。預防：maintenance.md §5 要求改制度檔後派 verifier read-back；引用盡量單向（其他檔引 diagnosis/dispatch，不回引）。
